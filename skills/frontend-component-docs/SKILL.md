# Frontend Component Documentation

Applies to reusable components in `<ui-packages-dir>`. A component nobody can find or
use correctly is not reusable, whatever its code quality.

## Resolving project conventions

Values in angle brackets come from the project's stack profile. Resolve them in this
order:

1. Read `STACK-PROFILE.md` at the repo root and use its values verbatim.
2. If it is absent or a key is missing, infer from the repo — `ui-scope`,
   `primitives-pkg`, and `wrappers-pkg` from existing package names under
   `<ui-packages-dir>`. A `components.json` in a package marks it as vendored.
3. If still unresolved, match the dominant convention already present in the repo.
4. Only when the repo is empty, fall back to this skill's stated default — then write
   the chosen values into `STACK-PROFILE.md`.

Never invent a new convention when the repo already expresses one.

Storybook is the assumed documentation surface. Where a project does not use it, the
README, JSDoc, and accessibility rules still apply in full — only the stories section
drops. Do not treat its absence as permission to skip the rest; the README and the
exported prop types are what a consumer reads first either way.

The vendored-primitive exemption in `frontend-architecture` rule 11 governs which files
these rules reach. Read it before documenting anything under `<primitives-pkg>`.

## Hard rules

### 0. Document the layer consumers import

Where primitives are vendored — generated by `shadcn add` or an equivalent — the
documented surface is `<wrappers-pkg>`, not `<primitives-pkg>`. That is the layer
consumers import, the layer whose API the project actually controls, and the only
layer where a doc comment survives the next generator run.

| Layer | What gets documented |
| ----- | -------------------- |
| `<theme-pkg>` | Package README: the token list, theme selectors, how to add a theme |
| `<primitives-pkg>` | Package README only: which primitives are vendored, at what version, from which registry. **No per-component docs** — the files are not authored here |
| `<wrappers-pkg>` | Everything below: per-component README, JSDoc, stories, accessibility contract |
| `<utils-pkg>` | Package README plus JSDoc on every exported function |

A vendored primitive that has no wrapper yet needs no per-component documentation. It
is upstream's component, documented upstream. The moment the project wraps it to change
a default, add a size, or fix a behaviour, that wrapper is a project component and rule
1 applies to it in full.

### 1. Every component has a README

Purpose in one sentence, when to use it versus the alternatives, import line, a
complete props table, copy-paste examples, accessibility notes, and keyboard
behavior where the component is interactive.

Where a wrapper only narrows or extends a documented upstream component, say so and
link upstream rather than restating the whole prop table — but document every prop the
wrapper adds, changes the default of, or removes.

### 2. A story per variant and per state

- One story per meaningful use case, not one story per component.
- Title hierarchy `Category/Component`, so the sidebar stays navigable.
- Controls wired through `argTypes` for every interactive prop.
- A `Default` story, and a story showing all variants side by side.
- Realistic content. Placeholder Latin hides layout problems that real text exposes.

### 3. Types are documentation

- JSDoc above every prop, stating what it does and defaulting behavior.
- Discriminated unions where props are variant-specific, so impossible combinations
  do not typecheck.
- Optional props marked, with sensible defaults.
- Prop types exported so consumers can build on them.

### 4. Examples beat prose

Show the common cases, the error state, the loading state, and the edge cases.
Interactive controls let a consumer answer their own question faster than any
paragraph.

### 5. Accessibility is documented, not assumed

State the conformance level, list keyboard interactions, name the ARIA attributes the
component sets, and describe what a screen reader announces. A consumer needs to know
which parts are handled and which are theirs.

### 6. Documentation ships with the change

JSDoc lives in the code and moves with it. The README is part of the pull request,
not a follow-up. Breaking changes get a version bump.

## Layout

Follow the layout the package already uses. Where primitives come from a generator, its
convention wins inside `<primitives-pkg>` — fighting it means every regeneration
produces a rename.

```
<ui-packages-dir>/<primitives-pkg>/      # vendored — generator's layout, untouched
  src/
    components/ui/
      button.tsx
      input.tsx
    lib/utils.ts
    index.ts
  README.md                              # what is vendored, from where, at what version
  components.json                        # the generator's own config

<ui-packages-dir>/<wrappers-pkg>/        # authored here — documented in full
  src/
    components/ui/
      button.tsx                         # wraps the primitive
      button.types.ts                    # exported prop types with JSDoc
      button.stories.tsx
      README.md
    index.ts
  README.md
  docs/
    components.md                        # index of everything the package exports
```

Where a project authors its primitives rather than vendoring them, the older
one-directory-per-component layout is equally valid:

```
src/button/{button.component.tsx,button.types.ts,button.stories.tsx,README.md}
```

Pick whichever the repo already expresses and stay with it. Two layouts in one package
is the only wrong answer.

## Props with JSDoc

```tsx
// button.types.ts
import type { ButtonHTMLAttributes, ReactNode } from "react";

/**
 * Visual weight of the button.
 * - `primary`: the main action on a screen. At most one per view.
 * - `secondary`: an alternative action shown alongside a primary.
 * - `ghost`: tertiary action with minimal visual weight.
 */
type ButtonVariant = "primary" | "secondary" | "ghost";

/**
 * Size preset controlling padding and type scale.
 * - `sm`: dense layouts and toolbars.
 * - `md`: the default, correct for most cases.
 * - `lg`: touch-first surfaces and prominent calls to action.
 */
type ButtonSize = "sm" | "md" | "lg";

type ButtonProps = ButtonHTMLAttributes<HTMLButtonElement> & {
  /**
   * Visual weight.
   * @default "primary"
   */
  variant?: ButtonVariant;

  /**
   * Size preset.
   * @default "md"
   */
  size?: ButtonSize;

  /**
   * Shows a progress indicator and blocks interaction.
   * @default false
   */
  isLoading?: boolean;

  /**
   * Stretches the button to its container's width.
   * @default false
   */
  isFullWidth?: boolean;

  /**
   * Replacement label announced and displayed while loading.
   * @example "Saving…"
   */
  loadingText?: string;

  /** Icon rendered before the label. */
  icon?: ReactNode;

  /**
   * Accessible name. Required when the button renders only an icon,
   * since there is no text for assistive technology to announce.
   */
  ariaLabel?: string;

  /** Button content. Omitted for icon-only buttons. */
  children?: ReactNode;
};

export type { ButtonProps, ButtonSize, ButtonVariant };
```

## Component README

````markdown
# Button

Triggers an action. Use for form submission, dialog confirmation, and any
call to action that does not navigate.

## When to use

| Component | Use for |
| --------- | ------- |
| `Button` | Actions — submit, confirm, delete |
| `Link` | Navigation to another route or document |
| `IconButton` | Icon-only actions in dense toolbars |

If activating it changes the URL, it is a link, not a button.

## Import

```tsx
import { Button } from "<ui-scope>/<wrappers-pkg>";
```

## Props

| Prop | Type | Default | Description |
| ---- | ---- | ------- | ----------- |
| `variant` | `"primary" \| "secondary" \| "ghost"` | `"primary"` | Visual weight |
| `size` | `"sm" \| "md" \| "lg"` | `"md"` | Size preset |
| `isLoading` | `boolean` | `false` | Shows progress, blocks interaction |
| `isFullWidth` | `boolean` | `false` | Stretches to the container |
| `loadingText` | `string` | — | Label shown while loading |
| `icon` | `ReactNode` | — | Icon before the label |
| `ariaLabel` | `string` | — | Accessible name; required when icon-only |
| `disabled` | `boolean` | `false` | Blocks interaction |
| `onClick` | `(event: MouseEvent) => void` | — | Activation handler |

## Examples

Basic:

```tsx
<Button onClick={handleSubmit}>Submit</Button>
```

Variants:

```tsx
<Button variant="primary">Save changes</Button>
<Button variant="secondary">Cancel</Button>
<Button variant="ghost">Skip</Button>
```

Async action with progress:

```tsx
import { useState } from "react";

import { Button } from "<ui-scope>/<wrappers-pkg>";

// Wraps Button with a saving state driven by the caller's async action.
const SubmitButton = ({ onSave }: { onSave: () => Promise<void> }) => {
  const [isSaving, setIsSaving] = useState(false);

  const handleClick = async () => {
    setIsSaving(true);

    try {
      await onSave();
    } finally {
      setIsSaving(false);
    }
  };

  return (
    <Button isLoading={isSaving} loadingText="Saving…" onClick={handleClick}>
      Save
    </Button>
  );
};
```

Icon-only, which always needs a name:

```tsx
import { X as CloseIcon } from "lucide-react"; // any icon source works

<Button variant="ghost" icon={<CloseIcon />} ariaLabel="Close dialog" />
```

## Accessibility

- **Conformance**: WCAG 2.1 AA
- **Element**: renders a real `<button>`; `type` defaults to `"button"` so it never
  submits a form by accident
- **Keyboard**: `Tab` to focus, `Enter` or `Space` to activate
- **Focus**: visible ring via `focus-visible`, so it appears for keyboard users and
  not on mouse click
- **Screen reader**: announces its text content, or `ariaLabel` when icon-only
- **Loading**: `loadingText` replaces the label and the button becomes disabled
- **Motion**: colour transitions are gated behind `motion-safe`
````

## Stories

The story requirements are hard rule 2 above: a `Default` story, one story per
meaningful use case, all variants side by side, every interactive state, controls
wired through `argTypes`, and one realistic composition. A complete
`button.stories.tsx` example is in
[`references/stories-example.md`](references/stories-example.md).

## Storybook setup

The `.storybook/main.ts` configuration — including the accessibility addon — is
shown in [`references/stories-example.md`](references/stories-example.md).

The accessibility addon reports per-story violations while you build. It does not
replace the automated scan in the end-to-end suite, which checks components in a real
page with real focus order — see `frontend-testing`.

Component behavior is verified by Playwright against a running application, never by
a JSDOM render test. `frontend-testing` explains why, and owns that boundary.

## Checklist

Before merging any component:

- [ ] Implementation complete and covered by an end-to-end flow
- [ ] JSDoc on every prop, including defaults and examples
- [ ] README with purpose, when-to-use comparison, import line, full props table,
      three or more realistic examples, and related components
- [ ] Stories: `Default`, all variants, all sizes, every interactive state, and one
      realistic composition
- [ ] Icon-only usage documented as requiring an accessible name
- [ ] Accessibility section: conformance level, keyboard table, ARIA attributes,
      screen-reader behavior
- [ ] Prop types exported from the package barrel
- [ ] Version bumped if anything changed shape
